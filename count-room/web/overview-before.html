Worked example: how to narrate an architecture pitch

Scenario a partner might ask you to solve live: "A GSI wants to build an AI claims-processing assistant for an insurance client." Walk it in this order:

  1. Model choice — Sonnet-class model for routine document extraction (cost/latency balance); escalate to Opus-class reasoning for ambiguous or high-value claims.

  2. Context & retrieval — connect Claude to the claims database and document store via MCP, so it retrieves only the relevant claim's context.

  3. Tool use — the agent calls dedicated extraction and validation tools rather than freeform reasoning over raw documents.

  4. Guardrails — require human approval above a claim-value threshold; run evals to catch hallucinated fields before they reach a human.

  5. Delivery via the GSI — the GSI packages this as a managed offering, integrating it into the client's existing systems, running it on Bedrock if the client is already an AWS shop.

The point of narrating it this way: it shows you can move from a vague ask to a concrete, partner-deliverable architecture — which is the actual job.

The current frontier

The AI-native SDLC

Anthropic's AI-Native SDLC Playbook is the sharpest published articulation of where this is going, and it is worth knowing cold for both interviews — it's Anthropic's own point of view, and it's the frame a Cursor customer will increasingly bring to the table.

The diagnosis: organizations adopted AI coding tools but kept the old approval gates and handoffs. The build phase got dramatically faster; review, testing and deployment stayed at human speed — so the gates became the bottleneck. The fix isn't more gates. It's turning the line into a loop, with AI embedded at every point and human judgement concentrated at the decisions that actually need it.

Governance, and why it's the interesting part

Separation of duties survives

“The agent that wrote the code has no way to approve it.” The oldest control in enterprise software still holds — it just gets enforced between agents rather than between humans.

Detection stays deterministic. The playbook is explicit that control-breach detection uses metrics and statistical rules, not model-driven judgement, at that gate. Same instinct as Pit Boss's policy gate.

Regulated code is carved out, not exempted

Layers of agentic review, with human review reserved for regulated and critical code. Pre-approved runbooks the agent may trigger only at defined tiers. In regulated shops, managed settings deployed by MDM that engineers cannot override.

This is the paragraph to quote when a customer says “we could never let an agent near our codebase.” Nobody is asking them to. They're being asked to say which code is which.

Metrics and maturity

Leading indicators — speed

Time from intent to committed artifact. Time to first review, measured in minutes. These move first and tell you the loop is actually closing.

Lagging indicators — quality

Rework cycles. Defects escaping to production. Survival rate of requirements. These are what an executive sponsor will actually judge the program on.

Maturity is modular, not sequential. The plays form a dependency graph rather than a ladder: start with any play nothing points into, and progress by prerequisite. The direction of travel is always the same — “first, you prompt each step by hand, with the end state being a loop in which each accepted artifact fires the next gate.”

And the closing line, which is the one to have ready when someone asks whether this replaces engineers: “The loop keeps running. Human judgement stays above it.”

Branches and commits, visually

A commit is a saved snapshot of your code with a message describing what changed. A branch is just a movable pointer to a line of commits — it lets you work on something new without touching the stable code.

main
feature/x

The everyday branch & commit workflow

  1. Branch off main — create an isolated line of work so main always stays deployable.

    git checkout -b feature/checkout-retry

  2. Stage your changes — pick exactly which edited files go into the next snapshot.

    git add src/checkout.py

  3. Commit — save a snapshot locally with a message explaining the "why."

    git commit -m "Retry checkout on transient network errors"

  4. Push the branch — upload your commits to the shared remote (e.g. GitHub) so others can see them.

    git push -u origin feature/checkout-retry

  5. Open a Pull Request (PR) — propose merging your branch into main. This is where CI runs and teammates review the diff.

  6. Merge (or squash-merge) — once checks pass and the PR is approved, the commits join main. Branch protection rules typically block a merge until CI is green.

  7. Delete the branch — its job is done once merged; the commit history lives on inside main.

    git branch -d feature/checkout-retry

Merge vs. rebase

Merge

Combines two branches with a new merge commit. Preserves full, honest history — you can see exactly when and how work came together.

git merge feature/x

Rebase

Replays your branch's commits on top of the target branch, producing a clean, linear history with no merge commit.

git rebase main

Golden rule: never rebase commits that others have already pulled — it rewrites commit hashes and breaks shared history. Safe on your own local/unshared branch; use merge (or squash-merge) once a branch is pushed and shared.

Why branches matter for the SDLC

Isolation

Work-in-progress never destabilizes main, so the team can always ship what's on it.

Review gate

A PR is the checkpoint where humans and CI both inspect a change before it becomes permanent.

Traceability

Every change is a commit with an author, message, and diff — the audit trail CI/CD and rollbacks depend on.

Part 0 — the setup check

Before anything runs, the script verifies two things people constantly conflate. It refuses to continue if the first is missing.

Commit identity

The name and email stamped onto every commit. It is a label, not a login — git will let you type anyone's name.

git config --global user.name "Mike Malveira"
git config --global user.email "mike.malveira@gmail.com"

That email must be verified on your GitHub account, or your pushed commits show an anonymous author and never reach your contribution graph.

Authentication

Proof to GitHub that you are mikemalv and may push. An SSH key, or a token in the macOS Keychain.

brew install gh && gh auth login

Stores an OAuth token in the Keychain and configures git's credential helper. No credential is ever stored in the tutorial files. See CREDENTIALS.md.

Part 1 — make a repository on your own machine

01
mkdir -p git-practice && cd git-practice && pwd

What: Creates an ordinary empty folder next to the script and moves into it.

Why: Nothing git-specific yet. Git works on whatever folder you point it at — there is no project registry and no server involved.

02
git init -b main

What: Turns the folder into a git repository, with the first branch named main.

Why: Creates the hidden .git folder. Everything git knows about this project lives in there — delete it and you have a plain folder back. GitHub expects main, so name it now rather than renaming later.

03
ls -a

What: Lists everything, including hidden entries.

Why: There it is: .git. That single directory is the repository. The rest of the folder is just your files.

04
git status

What: Reports what has changed and what is staged.

Why: You will type this more than any other git command. When you are lost, run it — it tells you where you are and usually prints the exact command you need next.

Part 2 — stage files and make the first commit

05
printf ... > README.md ; printf ... > notes.md ; printf ... > .env ; ls -a

What: Creates two files we want in the repo, and one that must never go in.

Why: The .env is deliberate. Committing a credential is the most common real mistake in git, and once pushed you must treat it as leaked — rotating the secret, not just deleting the file.

06
printf '.env\n*.log\n' > .gitignore && cat .gitignore

What: Lists patterns git should pretend it cannot see.

Why: Write this before your first commit. .gitignore only stops files being added — it has no power over files git already tracks, so it cannot un-commit a secret afterwards.

07
git status --short

What: The compact view. ?? means git has never seen this file.

Why: Notice .env is missing from the list entirely. That is .gitignore working. Keeping status quiet is what makes the signal in it useful.

08
git add README.md notes.md .gitignore

What: Copies the current contents of these three files into the staging area.

Why: Name files explicitly while learning. git add . stages everything including things you never looked at — which is exactly how a forgotten .env ends up committed.

09
git status --short

What: A in the first column means staged and ready.

Why: The staging area is git's best feature: it lets you commit a deliberate, coherent set of changes rather than everything you happened to touch today.

10
git diff --staged

What: Shows exactly what is about to go into the commit.

Why: Your last chance to catch a debug print, a stray key, or a deletion you did not mean. Plain git diff shows the opposite — what is not yet staged — which is why it looks empty at this point and makes people think git is broken.

11
git commit -m 'Initial commit: README, notes and gitignore'

What: Records the staged snapshot permanently in .git.

Why: A commit stores a full snapshot plus its parent, author, timestamp and message, identified by a SHA hash. Still entirely local — nothing has touched the internet yet.

12
git log --oneline

What: One line per commit: short SHA and message.

Why: That SHA is the commit's permanent address. The first 7 characters work anywhere git expects a commit reference.

Part 3 — put it on GitHub

The first command here depends on your setup. With the GitHub CLI it is one line; by hand it is three.

13
gh repo create mikemalv/git-practice --private --source=. --remote=origin --push

What: Creates the repo on GitHub, adds it as origin, and pushes main — all at once.

Why: The fastest path from a local folder to a repo on GitHub. --private keeps practice work off your public profile. Done by hand it is three steps: create the empty repo at github.com/new, then git remote add origin git@github.com:mikemalv/git-practice.git, then git push -u origin main. The -u is the part people skip — it records the link so later git push needs no arguments.

14
git remote -v

What: Lists the remotes this repo knows about, with fetch and push URLs.

Why: The fastest way to answer "where would a push actually go?". Worth checking before your first push to any repo you care about. origin is a convention, not a keyword.

15
git log --oneline --decorate -1

What: Shows the latest commit with the labels pointing at it.

Why: Look for both main and origin/main. On the same commit means your machine and GitHub agree. When they drift apart, that is exactly what push and pull are for.

Part 4 — the everyday loop

Edit, add, commit, push. This is the cycle you will run hundreds of times a week; everything else in git is an exception to it.

16
printf '\n## Progress\n...' >> README.md && git status --short

What: Edits a file git is already tracking. M means modified.

Why: Note the difference from earlier: ?? was a file git had never seen; M is a tracked file that has changed.

17
git diff

What: Shows what changed in your working tree versus the last commit.

Why: + lines added, - removed. Read this before staging — it takes seconds and catches a lot.

18
git add README.md && git commit -m 'Add a progress section to the README'

What: Stages the change and commits it.

Why: Once files are already tracked you can do both at once with git commit -am "msg". That shortcut only picks up tracked files though — brand new files always need an explicit git add.

19
git push

What: Uploads the new commit to GitHub.

Why: No arguments needed, because -u earlier recorded where main belongs.

20
git log --oneline --decorate -2

What: Confirms main and origin/main are level again.

Why: Both labels on the same commit means GitHub has everything you have.

Parts 5 and 6 — branch, then merge back

A branch is not a copy of your files. It is a movable label pointing at one commit — which is why creating one is instant no matter how big the repo.

The branch and merge commands

21
git switch -c feature/add-changelog

What: Creates a branch at the current commit and switches onto it.

Why: Nothing was copied; git wrote a small file containing a SHA. Older spelling is git checkout -b, which you will still see everywhere. Slashes in branch names are just a grouping convention.

22
git branch

What: Lists local branches; * marks the one you are on.

Why: Two branches, both pointing at the same commit. They only diverge once you commit on one of them.

23
printf '# Changelog...' > CHANGELOG.md && git add CHANGELOG.md && git commit -m 'Add a changelog'

What: Does some work and commits it — on the branch, not on main.

Why: This commit exists only on feature/add-changelog. main has no idea it happened.

24
git log --oneline --decorate --graph --all -4

What: Shows both branches and where each label sits.

Why: The feature branch is now one commit ahead of main. This is what "diverged" looks like.

25
git push -u origin feature/add-changelog

What: Pushes the branch to GitHub and links it.

Why: Branches are pushed individually — pushing main does not push your other branches. On a real team this is the moment you would open a pull request: gh pr create --fill, then gh pr merge --squash. We merge locally instead, so you can see the mechanics a PR sits on top of.

26
git switch main && ls

What: Switches back to main.

Why: CHANGELOG.md has vanished from the folder. It is not lost — it simply does not exist in this version of history. Switching branches rewrites your working tree to match whatever that branch points at. This is the single most disorienting thing for beginners, and it is worth watching happen.

27
git merge feature/add-changelog

What: Brings the branch's commit into main.

Why: A fast-forward — main gained no commits of its own, so git just slides the label. No merge commit needed because there was nothing to reconcile. See the left-hand diagram above.

28
ls && git log --oneline --decorate --graph -4

What: CHANGELOG.md is back, and main contains the branch's work.

Why: Confirms the merge did what you expected before you push it anywhere.

29
git push

What: Sends the merged main to GitHub.

Why: Merging locally does not update GitHub. Nothing reaches the remote until you push.

30
git branch -d feature/add-changelog

What: Deletes the local branch label now its work is merged.

Why: -d refuses if the branch has unmerged commits — a useful safety net. Deleting a branch never deletes commits; it only removes the label pointing at them.

31
git push origin --delete feature/add-changelog

What: Deletes the branch on GitHub too.

Why: Local and remote branches are separate namespaces. Deleting one has no effect on the other, which surprises people constantly.

32
git log --oneline --decorate --graph --all -6

What: The finished history.

Three rules worth memorising

  1. Never rewrite history someone else has pulled. rebase, commit --amend and push --force all rewrite. Excellent on your own unpushed branch; an incident on main. Use --force-with-lease instead of --force — it refuses if the remote moved since your last fetch.

  2. git clean and reset --hard have no undo for uncommitted work. reflog recovers commits. It cannot recover changes you never committed. Always run git clean -n first.

  3. Commit before you experiment. A commit is free and reversible. An uncommitted afternoon is not.

The bet — and why

Most candidates will build "agent reads Sentry alert → agent opens PR." That earns one polite nod and then a question they can't answer: "we'd never let that near our codebase — then what?"

The obvious build

An agent that can fix anything. Impressive for ninety seconds, undeployable in any regulated enterprise, and it has no answer to the governance question.

The opinionated build

The fix is not the hard part. Routing the fix through a governance boundary is. An agent that can change any file is an agent that never gets turned on.

The climax of the demo is not the agent fixing something. It is the agent refusing to. Everyone else shows an agent doing more; this one knows where to stop and can prove why. For a Field Engineering role that is the whole point — this artifact is exactly the reference architecture an FE would put in front of a regulated customer.

Why gaming makes the constraints real

A casino platform never has a maintenance window. The five decisions you will be asked to defend

  1. The policy gate is deterministic code, not a model call. The LLM is used everywhere except the one place where being wrong is a regulatory violation. Path globs → zones, in version-controlled YAML a compliance officer can review without reading TypeScript.

  2. Triage is read-only by construction — via the SDK's tools allowlist, not by asking nicely in the prompt. Capability boundaries you can enforce beat instructions you can only hope are followed. This is also the prompt-injection answer: a stack trace is attacker-influenceable input, so the agent that reads it first cannot write.

  3. The security agent is a separate agent, on a separate model, with no shared context. The fix agent cannot grade its own homework. Costs latency and tokens; buys independence.

  4. Async and resumable. Real incident response has multi-hour human waits. Agent.resume() means a run started at 02:00 survives until someone approves it at 09:00 — process restarts included.

  5. Everything is data, not code — zones, agent specs, model routing, runtime. Which is also how you survive the live-extension prompt.

Playbook alignment & one real constraint

Drift Fleet in AI-native SDLC terms

The AI-Native SDLC Playbook's central mechanic is that every stage commits an artifact the next stage reads, and an accepted artifact fires the next gate. Drift Fleet's rollout plan is that idea made explicit and cross-repo: the DAG is the gate-firing order, written down.

What the playbook saysWhat Drift Fleet is
Each accepted artifact fires the next gate.The wave sequencer. A destructive producer step is structurally unable to fire until every consumer migration in earlier waves has merged.
Detection uses deterministic rules, not model judgement, at the gate.The contract differ and the policy. Type widening is proved, not guessed; an inferred rename below the confidence floor is refused outright.
Human review reserved for regulated and critical code.The SOX-scoped repo: change dossier, never a PR, even for trivially safe changes.
Parallel sessions and subagents.The per-repo scout and migrate fan-out.
Correction worth carrying into the room. Cloud runtime is not a one-line flag flip for this build, and the docs are explicit: “Custom tools are local agents only. Cloud agents ignore local.customTools at creation and throw a ConfigurationError when you pass it on send().” The scouts use a custom tool (emit_refs) for structured output — which means the per-repo cloud fan-out, the headline capability of this build, does not work as currently scaffolded.

The fix, and why it's worth mentioning unprompted: inline mcpServers work in both runtimes, so the structured-output channel moves from a custom tool to a small inline MCP server. One caveat to remember out loud: inline MCP servers aren't persisted across Agent.resume(), so you repass them on reconnect. Volunteering a constraint you hit and routed around reads as someone who built on the SDK rather than someone who read the landing page.

    Two design details worth volunteering
    
          
    
            
    
              
    The gate fails closed
    
              
    An untagged object that lives in a schema containing tagged objects escalates rather than defaulting to STANDARD. So does a tag lookup that errors. Defaulting an unknown to "safe to automate" is how a governance system quietly stops governing.
    
            
    
            
    
              
    The agent has no write path to the rule
    
              
    Because the zone lives in warehouse tags and every analysis agent holds a read-only role, the fix agent cannot relabel its way out of a zone. Had the tags lived in a repo file, it could have edited them. This is the strongest single argument for the tag-based design, and it is the first hole a good interviewer probes.

    The difference that actually decides deals
    
          
    
            
    
              
    Cursor: the cloud runtime
    
              
    "Runs in an isolated VM with your repo cloned in. Cursor runs the VMs." Best "when the caller doesn't have the repo, you want many agents in parallel." That is the capability with no equivalent on the other side — Cortex Code is a local CLI subprocess pointed at one working directory.
    
              
    Everything fleet-shaped follows from this: one agent per repo, per module, per service, without the orchestrator holding checkouts or the caller having filesystem access. Plus codebase indexing, semantic search, and a model router with optimize_for.
    
            
    
            
    
              
    Cortex Code: identity and the control surface
    
              
    It authenticates as a Snowflake principal with SQL and warehouse tools already built in — no second credential story, no tool you have to write. For work whose centre of gravity is the warehouse, that is a shorter path.
    
              
    And its programmatic controls are genuinely stronger: a real canUseTool callback, lifecycle hooks in code, plan mode, and JSON-schema output without inventing a tool to carry it.
    
            
    
          
    
        
    

        
    
          
    What this means for your build
    
          
    Two of these constraints land directly on the prototypes, and both are worth raising before an interviewer finds them.
    
          
    
            
    
              
    ConstraintEffect on your prototypeWhat to say
    
              
                
    Tool allowlists are local agents only"Read-only by construction" — the load-bearing claim in every one of your builds — is a local runtime guarantee. A cloud agent cannot be restricted this way.Triage stays local by design; that is a deliberate placement, not an oversight. Cloud runtime is for the write-side fan-out, where the bound is the policy gate rather than the tool list.
    
                
    Custom tools throw on cloud agentsStructured output via emit_triage / emit_refs does not survive a move to cloud runtime.Move that channel to an inline MCP server — those work in both runtimes. Repass them on resume(), since inline servers are not persisted.
    
                
    Hooks are file-based, no programmatic callbackYou cannot intercept a tool call in code the way canUseTool allows on the other SDK.This is exactly why your gate sits between stages rather than inside the agent loop. Architecturally it is the stronger pattern anyway — the decision is auditable and testable without running an agent.
